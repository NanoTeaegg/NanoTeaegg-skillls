# 设计推演:从「想做一套设计规范系统」到现在这套格式

这份文档记录 `webui-design-system`(原 `ui-design`)这次重构背后的思考过程——我们怎么从一个**小工具网站 UI 一致性解决不了**的具体痛点，一步步推到现在这套「token + 组件库 + 固定外壳预览 + 变更脚本」的格式。给后来维护这个 skill 的人看，避免把已经否定过的方案再走一遍。

---

## 0. 起点:小工具网站的 UI 一致性问题

原来的 `ui-design` 能生成一套 `UI_SPEC.md` + `tokens.css` + `preview.html`，但实际用下来有两个硬伤:

1. **效果不够专业**:`preview.html` 是模型每次从零手搓的，质量全靠即兴发挥，不稳定。
2. **只是一次性产物**:输出一次 UI 界面就完事了，没法**约束后续页面**，也没法**追溯 UI 变更**。

想要的东西很明确:一套能**约束项目 UI、能观测 UI 变更**的设计系统。参考过 TDesign 那种设计系统，但结论是——

> **对小项目，TDesign 太重（独立发包、版本化组件库），一个 HTML 文件又太轻（无法完整承载视觉预览和变更追溯）。**

所以真正的问题是:**在「TDesign」和「单 HTML」之间，那个刚好的中间态长什么样？**

---

## 1. 第一层纠偏:三份手写文件必然漂移，preview.html 零约束力

最初的产物是三份**各自手写、靠模型每次保持一致**的文件(`UI_SPEC.md` / `tokens.css` / `preview.html`)。问题根因:

- 三份文件之间没有任何机器关系 → **必然漂移**。
- 专业度靠模型每次即兴 → **不稳定**。
- 变更只有一张手写的 markdown 表 → **不可校验、不可 diff**。

关键认知 ——**`preview.html` 是镜子，不是法律**:

> 没有任何业务页面会 import `preview.html`。你改它，没有任何页面会跟着变；你写业务页面时不读它，也不会报错。所以**约束力从来不来自 HTML**。这正是「单 HTML 太轻」的本质——它是观测层，约束层根本不在它身上。

由此厘清三类文件各自能干什么:

| 文件 | 约束力来源 | 可约束 | 可观测变更 |
|---|---|---|---|
| **token 代码文件**（tokens.css） | 业务代码**真的 import 它**（`var(--x)`） | ✅ 唯一有「自动约束力」的文件 | ✅ 每个 token 一行，git diff 干净 |
| **UI_SPEC.md** | 靠「动手前必须读它」的纪律 + 评审 | ⚠️ 软约束 | ⚠️ 表格 diff 噪声大 |
| **preview.html** | 无 | ❌ 零约束力 | ✅ 但只能肉眼观测 |

**结论**:真正让后续页面照设计系统走的，**只有一件事——业务代码物理引用 token 文件**。tokens.css 才是有「引力」的事实源；UI_SPEC 是契约；preview.html 是观测窗。

---

## 2. 第二层认知:一个完整设计系统是三层，不是一层

光有 token 不够。一个完整的设计系统还包括组件和交互——折叠面板的动效、评论组件的交互效果等等。所以它分三层:

| 层 | 内容 | 事实源在哪 |
|---|---|---|
| **1. Token 层** | 色/字/间距/圆角/阴影/层级 **+ 动效时长和缓动曲线** | token 代码文件（tokens.css） |
| **2. 组件规范层** | 组件的 API/变体/状态 **+ 行为与动效编排** | `UI_SPEC.md` |
| **3. 组件实现层** | 真正能跑的折叠面板、评论组件 | **项目自己的组件代码**，不是设计系统，更不是 preview.html |

**要害:组件「行为」的事实源，绝不能是静态 preview.html。**

> 如果折叠面板的动效既在真实组件里、又在 preview.html 里被重画一遍 mock，这俩**必然漂移**，而且行为比 token 值更难手动对齐。

「折叠面板的动效」该怎么被设计系统管？拆成三件、各归其位:

1. **时长 + 缓动曲线 → token**：`--motion-duration-expand`、`--ease-standard`，不准写魔法数字。
2. **行为编排 → UI_SPEC 规范**：「点 header 切换；内容 220ms ease-standard 展开…」。
3. **能跑的实现 → 项目里那一份组件**，它消费上面的 token、遵守上面的规范。

**设计系统管三层，但只「拥有」前两层的实现（token 文件 + UI_SPEC）；第三层归属项目组件代码，设计系统通过 token + spec + 文档去约束和观测它，而不是重画。**

---

## 3. 第三层判断:小工具别把组件定死

对一个常规小工具网站，逐组件把 API/变体/状态/动效全部前置定义，是**过度工程**——还不知道会用到哪些组件，维护规范的成本比建组件还高。

值得「定死」的只有两样，因为它们便宜、且有自动引力:

1. **Token 层**（色/字/间距/motion）——地基，定义一次，代码 import 它，所有 UI 自动一致。
2. **一页基础 UI 约定**（十几条硬规则，不是逐组件矩阵）：只准用 token、按钮/输入/间距基线、状态必须有非颜色信号、暗色策略、焦点可达。

**组件不前置定死。** 工作流是:

> 第一次需要折叠面板？直接建，守住 token 和基础约定就行，不用写规范。
> **同一个组件第二次要用时**，才把它回收进 `components.css` 和文档站标准化。

即 **token 是「急性子」（前置定义），组件是「慢性子」（用例催生）**。这样既不会到处裸写样式，又不会被一堆用不上的组件规范拖死。

这也证明小工具不需要逐组件状态矩阵也能做到约束和可观测:
- **可约束** = token 有引力 + 一页基础约定 + lint 脚本（查裸 hex/px）。
- **可观测** = git diff token 文件 + diff 脚本生成 changelog。

---

## 4. 第四层边界:多端怎么分，为什么拆 skill

考虑桌面 + 移动 + 不同系统后，按层分共享是固定的:

| 层 | 能跨端共享吗 | 怎么处理 |
|---|---|---|
| **Token** | ✅ 共享一个源 | 一份源生成 web/iOS/Android 三端 token |
| **组件规范** | ✅ 共享一份 UI_SPEC | 各端照同一份 spec 实现 |
| **组件实现** | ❌ **原生端不能共享** | web 的 css、iOS 的 SwiftUI、Android 的 Compose 各一份 |
| **观测/预览** | ❌ 每端各自渲染器 | web 用 preview.html 渲染真实 class；原生用 Xcode/Compose preview |

**HTML 组件库的边界**:能当 web 端（含桌面 + 移动浏览器，响应式一份搞定）的真实组件库，零漂移；但**当不了 iOS/Android 原生组件的事实源**——一个 SwiftUI 按钮的源不可能是一段 HTML。

> 真正的原生多端，本质上就比单端重——这是问题本身决定的，不是工程偏好。

**决策**:web 和原生的产物根本不是一类东西，一个 skill 同时扛三端只会哪端都不深。所以:

- 本 skill 收敛成**纯 web** 设计系统，改名 `webui-design-system`。
- iOS/Android 等真要做 App 时**另起单独 skill**，现在不空建。
- 与已有 `web-design`（做页面/landing）和 `frontend-dev`（写业务代码）职责区分清楚。

---

## 5. 最终格式

**定位**:建立**可观测、可预览**的 web 设计系统，保持整个项目 UI 一致;**只要有 UI 变更就应该用它**。

**产物模型（Lite，纯静态零构建）:**

| 文件 | 角色 |
|---|---|
| `design-system/tokens.css` | 值源（色/字/间距/motion），被业务代码引用 |
| `design-system/components.css` | **组件库事实源**：每个可复用组件 = 一组 class，消费 token |
| `design-system/components.js` | （可选）组件行为：折叠/评论交互，单一行为源 |
| `design-system/preview.html` | **观测窗**：引用上面三者、渲染真实 class，**绝不重画** |
| `docs/UI_SPEC.md` | 精简契约 + 一页基础 UI 约定 + 变更记录 |
| `scripts/diff_tokens.py` | 对比两版 token/组件 → 生成 changelog（可观测） |
| `scripts/lint_tokens.py` | 查裸 hex/px/ms、查绕过组件库自写样式（约束） |

**两条铁规则:**

1. **不漂移**:`preview.html` 必须引用 `components.css`/`components.js` 并用真实 class 渲染，**绝不在 preview 里内联重写组件样式**。preview 是渲染器，不是第二份实现。
2. **专业度兜底**:打磨过的 `preview.html` 固定外壳（完整色阶 + 对比度徽章 + 复制 hex、间距/圆角/阴影可视标尺、组件状态网格、版本 hash）做成 skill 的 asset 模板，专业度由模板保证，不靠每次发挥；视觉参考 TDesign。

**组件哲学**:碰到再建 → 守 token + 基础约定 → 同一组件第二次用时才回收进 `components.css` 和 preview。
