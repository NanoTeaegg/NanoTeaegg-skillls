# 测试与质量(Testing Quality)

把已经明确的需求、交互和技术方案,落实成团队能运行、能维护、能在 CI 中把关的测试体系。这个 skill 回答的是:**要测什么、用什么层级测、自动化测试代码放哪里、如何运行、什么结果算过关**。它不回答"功能要不要做",也不替开发实现业务逻辑。

## 为什么需要这一步

PRD 里的验收标准如果没有落到测试,很快会变成没人执行的文字。技术方案里的风险如果没有对应的测试策略,上线前也很难发现。这个 skill 的价值是把上游文档和真实代码结构连起来:既产出 `docs/TEST_PLAN.md`,也补上合适粒度的自动化测试代码,让质量门禁可以被机器执行。

## 何时走哪条路径

先判断 `docs/TEST_PLAN.md` 是否已存在:

- **不存在** -> 走「新建测试体系」流程(读取文档和项目结构 -> 访谈 -> 产出 TEST_PLAN + 测试代码)
- **已存在**,且用户在新增功能、调整验收标准、修改技术栈或补测试覆盖 -> 走「测试方案变更」流程(原地更新 + 补/改测试代码 + 追加变更记录)

## 新建测试体系流程

### 第 1 步:读取上游文档和项目结构

优先检查并读取:

- `docs/PRD.md`:功能模块、优先级、验收标准、范围与非目标
- `docs/UX.md`:核心流程、界面状态、错误/空/加载态
- `docs/TECH_DESIGN.md`:平台范围、技术栈、模块划分、风险、质量要求
- `docs/SCHEMA.md`:数据约束、关系、迁移规范(如存在)

同时检查项目结构,不要只看文档:

- 包管理器与测试命令:`package.json`、`pnpm-lock.yaml`、`pyproject.toml`、`pytest.ini`、`go.mod`、`pom.xml`、`build.gradle`、`settings.gradle`、`Package.swift`、`*.xcodeproj`、`*.xcworkspace` 等
- 已有测试目录与配置:`tests/`、`__tests__/`、`e2e/`、`playwright.config.*`、`vitest.config.*`、`jest.config.*`、`pytest` 配置、Xcode schemes、Gradle variants、CI 配置
- 代码边界:前端页面/组件、后端 API、移动端界面、数据访问层、第三方集成封装

如果上游文档缺失,不要卡住;告诉用户缺少哪些输入,并用访谈补齐本阶段需要的信息。如果项目结构为空或只有文档,仍可先产出测试计划和建议的测试目录,但要把"尚未生成可运行测试代码"写进开放问题。

### 第 2 步:识别平台并读取对应参考

根据项目结构和 TECH_DESIGN 判断平台。只读取相关参考,避免把不相关工具链塞进上下文:

- Web 项目 -> 读取 `references/web-testing.md`
- iOS 项目 -> 读取 `references/ios-testing.md`
- Android 项目 -> 读取 `references/android-testing.md`
- 后端/API 项目 -> 读取 `references/backend-api-testing.md`
- 性能/安全/质量门禁 -> 需要时读取 `references/performance-security-testing.md`

多端项目可以读取多个参考,但 `TEST_PLAN.md` 要按平台分层写清楚,不要混成一个泛前端/泛客户端方案。

### 第 3 步:结构化访谈(别跳过)

不要只凭文档和目录直接写测试。测试策略依赖团队对风险、速度和维护成本的取舍。用当前平台可用的提问机制(如 AskUserQuestion)向用户提问,并**等用户回答后再写正式文档和测试代码**。不要替用户假设关键门禁。

**访谈原则:**

- 已经在 PRD/TECH_DESIGN 写清楚的就别重复问;一次问 2-4 个相关问题。
- 追着"什么失败最不能接受"问,而不是平均用力覆盖所有代码。
- 只有当下确实无法定夺、依赖外部决策的问题,才写进「开放问题与假设」。
- 如果用户要求"先随便补点测试",也要至少确认测试范围和是否允许新增测试依赖。

**必须覆盖的维度(自适应提问):**

1. **质量目标与风险优先级** — P0 验收标准里哪些最关键?哪些故障上线后代价最高?
2. **测试层级取舍** — 单元、集成/API、E2E、移动端 UI、性能 smoke 各自做到什么程度?
3. **允许的工具与依赖** — 是否沿用已有测试框架?是否允许新增 Playwright、Vitest、pytest、XCTest、Espresso、k6 等?
4. **环境与数据** — 测试数据怎么准备?是否有 mock、seed、测试账号、模拟器/设备、后端测试环境?
5. **质量门禁** — 覆盖率、失败阻断、lint/typecheck、性能阈值、CI 运行频率和超时时间。
6. **不做什么** — 明确哪些测试暂不覆盖,例如真实支付、真实短信、生产级压测、安全渗透测试。

### 第 4 步:产出 TEST_PLAN.md

访谈信息够了之后,读取 `assets/test-plan-template.md`,按它的结构产出文档,写入 `docs/TEST_PLAN.md`(若 `docs/` 不存在则创建)。内容用**中文**。

要点:

- **验收标准必须映射到测试点。** 用表格写清 PRD/UX 验收标准、测试层级、测试文件、测试数据、通过条件。
- **测试分层要有理由。** 默认遵循"大量小而快的单元/组件测试 + 关键集成/API 测试 + 少量端到端主路径"的思路,但要结合项目风险调整。
- **平台分开写。** Web、iOS、Android、后端/API、性能/安全各自写工具、目录、命令、覆盖范围和门禁。
- **每个测试代码产物都要登记。** 测试文件、覆盖场景、运行命令、是否已运行、当前结果都要写进计划。
- **边界写实。** 明确 AI 生成测试不能替代真人探索式测试、安全审计、可用性测试或真实生产压测。

### 第 5 步:生成自动化测试代码

在不改业务实现代码的前提下,按项目现有风格生成测试。优先沿用已有工具链;只有用户同意或项目明显缺失时才新增依赖/配置。

可生成的测试类型包括:

- 单元/组件测试:纯函数、领域逻辑、表单校验、组件行为
- 集成/API 测试:API 契约、权限、错误处理、数据库约束在测试库中的表现
- E2E/UI 测试:PRD P0 主路径、关键错误态、权限路径
- 移动端 UI 测试:iOS XCUITest/XCTest、Android Espresso/Compose UI Test
- 性能 smoke/load 脚本:关键接口或页面的轻量阈值验证

生成测试代码时:

- 把文件放到项目惯用测试目录,如 `tests/`、`__tests__/`、`e2e/`、`*.spec.ts`、`*.test.ts`、`ios/*UITests/`、`app/src/androidTest/`。
- 使用稳定选择器、语义定位或测试 ID;不要依赖脆弱的 CSS 层级或截图像素。
- Mock 外部不可控服务,但保留一条可在测试环境跑通的关键集成路径(如果项目已有环境)。
- 测试名要能追溯到验收标准或风险点。
- 不要通过修改业务代码让测试"变绿";如果发现业务缺陷,在结果里报告并标记测试失败。

### 第 6 步:运行与修正测试

尽量运行低成本测试命令,例如 typecheck、unit test、单个 E2E spec、移动端可用的 dry run 或构建检查。运行失败时区分:

- **测试代码问题** -> 修正测试代码后重跑
- **环境/依赖缺失** -> 记录缺失项和用户需要执行的步骤
- **业务实现缺陷** -> 不擅自改业务代码;在 `TEST_PLAN.md` 的测试结果和最终回复中说明失败原因

产出后,简要告诉用户:TEST_PLAN 写到哪里、生成了哪些测试文件、跑了哪些命令、哪些通过/失败、下一步建议。

## 测试方案变更流程

当 `docs/TEST_PLAN.md` 已存在、用户要补测试、改质量门禁、功能验收标准变化或技术栈变化时:

1. **先读现有 TEST_PLAN.md** 和相关上游文档,理解当前测试体系。
2. **检查本次变更影响哪些测试层级和平台**,只改相关部分。
3. **原地更新 TEST_PLAN.md**,保持它是唯一最新的测试事实源。
4. **补充或修改测试代码**,优先最小范围覆盖新增/变更验收标准。
5. **运行相关测试命令**,记录结果。
6. **在「变更记录」表追加一行**:日期、类型(新增/删除/变更)、内容、原因。

## 边界:这个 skill 不做什么

- ❌ 功能范围、用户故事、产品验收标准 -> requirements-definition skill
- ❌ 用户流程、页面状态、视觉设计 -> ux-design skill 或设计工具
- ❌ 技术栈、架构、模块边界 -> dev-kickoff skill
- ❌ 数据库表结构、字段、索引、迁移脚本 -> database skill
- ❌ 业务实现代码、修 bug、重构生产代码 -> 开发实现阶段
- ❌ 完整安全审计、渗透测试、生产级容量压测 -> 专业安全/性能测试流程

如果用户要求直接修业务代码,先把失败测试和缺陷说明清楚,再询问是否进入实现/修复阶段。
