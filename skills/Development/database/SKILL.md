# 数据库设计与变更规范(Schema)

把需求和技术方案里隐含的数据,落成一份团队和 AI 都能据此建库、改库的设计文档。它要回答的是:**这个系统要存哪些数据、用什么存、怎么组织、怎么安全地演进**——不回答"用什么语言/框架写"或"功能上要做什么"。

## 为什么要先把 schema 定下来

数据结构是系统里最难改的部分:代码可以重构,但表一旦上线、灌满数据,再改字段类型、拆表、调关系都要付出迁移代价。很多项目的返工不是因为代码烂,而是因为一开始数据模型就没想清楚——该唯一的没唯一、该关联的关联错了、该预留的没预留。这个 skill 的核心价值是:**在建表之前,先把数据建模的关键决策问清楚(选型、主键、关系、隔离、软删除、敏感数据…),把每张表的约束和不变量写明确,并把变更规范定下来**,让 schema 从第一天起就是可演进的,而不是一笔糊涂账。

## 何时触发哪条路径

先判断 `docs/SCHEMA.md` 是否已存在:

- **不存在** → 走「新建 schema」流程(读输入 → 结构化访谈 → 产出 SCHEMA 文档)
- **已存在**,且用户在新增/修改/删除表、字段、索引或约束 → 走「schema 变更」流程(原地更新 + 追加迁移记录)

## 新建 schema 流程

### 第 0 步:读上游文档,别凭空建模

数据从需求来。动手前先读已有的上游文档,作为建模依据:

- `docs/PRD.md`(若存在)——里面的功能模块、实体、用户故事,是表和字段的来源。
- `docs/TECH_DESIGN.md`(若存在)——里面可能已定了语言/框架/ORM 和整体架构;尊重它已经做出的技术决策,不要推翻。

读到的关键实体、关系、约束先列个草稿,带着它去访谈——这样提问才有的放矢,而不是从零问起。如果上游文档都不存在,就基于用户当下的描述提炼实体,但要在「开放问题与假设」里说明:本设计未经 PRD/技术方案约束,后续可能需要回头对齐。

### 第 1 步:结构化访谈(关键步骤,别跳过)

不要拿到需求就直接甩出一堆 CREATE TABLE。数据建模里有大量决策一旦定错,迁移代价极高——这些必须先问清楚。

**访谈原则:**
- **自适应,不要机械念题。** 上游文档或用户已经讲清楚的维度就别再问;一次问 2-4 个相关问题,别一口气把九个维度全抛出来让人窒息。
- **追着"为什么"和"将来会怎样"问。** 用户说"存个用户表"时,真正要搞清的是:会不会多租户?要不要软删除?将来要不要审计谁改了什么?数据量会到多大?——这些决定了表长什么样、要不要预留字段、加什么索引。
- **必须拿到用户的真实答复再动笔。** 用 AskUserQuestion 提问后要**等用户回答**,不要自己替用户假设答案、也不要跳过提问直接写 schema——强制把数据建模的关键决策问清楚,正是这个 skill 的价值所在。只有那些当下确实无法定夺的事项(例如依赖尚未确定的数据量级、尚未做出的合规决策)才记进「开放问题与假设」;它是"现在没法定"的归档,不是"懒得问"的出口。

**需要覆盖的维度(用 AskUserQuestion 提问,给出带推荐的选项,降低用户负担):**

1. **数据库产品选型** — 关系型(PostgreSQL/MySQL…)、文档型(MongoDB…)、还是 KV/缓存?数据是强结构化还是灵活多变?有没有事务/强一致的硬要求?给出推荐和理由。若技术方案已选定,则确认沿用而非重选。
2. **核心实体与关系** — 从需求里提炼出哪些实体(用户、订单、商品…)?它们之间是 1:1、1:N 还是 N:M?N:M 要不要中间表、中间表上要不要带属性?
3. **主键 / ID 策略** — 自增整型、UUID、还是雪花/有序 ID?对外暴露 ID 吗(影响是否能用自增)?分布式写入吗?
4. **多租户 / 数据隔离** — 是否多租户?隔离策略:共享表 + tenant_id、独立 schema、还是独立库?这决定几乎每张表要不要带租户列。
5. **软删除与审计字段** — 删除是物理删还是软删(deleted_at)?要不要 created_at/updated_at/created_by 这类审计字段?要不要记录变更历史?
6. **数据规模与读写特征** — 各表预估数据量级?读多写多?有哪些高频查询/热点查询?——这直接决定索引、是否分区/分表。
7. **一致性、事务与并发** — 哪些操作必须在一个事务里原子完成?有没有并发写同一行的场景(需要乐观锁/版本号)?能接受最终一致的地方在哪?
8. **敏感数据与合规** — 存不存 PII / 支付 / 健康等敏感数据?要不要加密(列级/透明加密)?有没有数据保留期、删除/导出(GDPR 等)要求?
9. **变更与迁移约定** — 团队现有的命名约定(表名单复数、下划线/驼峰)、迁移工具、上线方式(能不能停机)、回滚预期?——决定「变更规范」章节怎么写。

### 第 2 步:产出 SCHEMA 文档

访谈信息够了之后,读取 `assets/schema-template.md`,按它的结构产出文档,写入 `docs/SCHEMA.md`(若 `docs/` 不存在则创建)。内容用**中文**,SQL 标识符/DDL 用英文。

要点:

- **表设计按「领域/模块 → 表」分层组织**,不要拉一个扁平的表清单:先按业务把表归到几个领域(如"账户""订单""通知"),再在每个领域下列出具体的表。每张表用**字段表 + 主键 + 关系 + 索引 + 约束/不变量**完整描述。
- **每张表都要有可检验的约束 / 不变量**,这是 schema 版的"验收标准"。一张只列了字段、没说清"哪些唯一、哪些非空、外键删了怎么级联、什么值不合法"的表,等于没设计清楚。例:`email 全局唯一`、`订单金额 amount >= 0`、`删除用户时其订单 deleted_at 一并置位(软删级联)`。
- **DDL 仅作示意,不绑定具体 ORM。** 可以给标准 SQL 的 `CREATE TABLE` 片段帮助理解,但这是设计文档不是迁移脚本;不要生成某个 ORM/迁移工具(Prisma/Alembic/Flyway…)的可执行代码——那是开发阶段的事。文档表达的是"设计意图与约束",工具实现交给落地。
- **选型要写理由。** 既然本 skill 负责数据库产品选型,就要把"为什么是 Postgres 而不是 Mongo"这类决策和权衡写进文档,而不只是甩个结论。
- **变更规范要写实**:命名约定、迁移流程(怎么加列、怎么改类型、大表怎么办)、回滚策略、向后兼容原则(先扩展后收缩等)。这是文档长期可维护的关键。
- 没问清楚的,如实写进「开放问题与假设」,不要假装确定。
- 文档头部填好状态、日期、负责人。

产出后,简要告诉用户:SCHEMA 写到哪了、做了哪些关键建模决策、有哪些开放问题需要他拍板,以及下一步通常是落地建表/写迁移或进入测试计划(由对应 skill 接手)。

## schema 变更流程

当 `docs/SCHEMA.md` 已存在、用户要新增/修改/删除表、字段、索引或约束时:

1. **先读现有 SCHEMA**,理解当前数据模型全貌,再动手——尤其要看清这次改动会不会影响已有关系、外键、唯一约束。不要在没读全的情况下改。
2. **评估迁移影响并提示用户**:这次变更是否破坏向后兼容?是否需要数据回填?大表上加索引/改列会不会锁表?——把风险讲清楚,必要时按访谈原则就迁移策略征求用户意见。
3. **原地修改对应表/字段定义**,保持文档始终是唯一、最新的事实源。
4. **在「变更与迁移记录」表追加一行**:日期、类型(新增表/加字段/改类型/加索引/删除…)、内容、迁移要点(是否需回填、能否回滚、是否兼容)、原因。这张表要让任何人能看懂"这张表为什么长成现在这样、怎么一步步演进过来的"。
5. 如果这次变更带出了新的不确定点,同样追加到「开放问题与假设」。

## 边界:这个 skill 不做什么

本 skill 只负责**数据持久层**。明确把这些留给其他阶段,避免越权:

- ✅ **属于本 skill**:数据库产品选型(关系型/文档型/KV + 具体产品及理由)、表/字段/关系/索引/约束设计、变更与迁移规范。
- ❌ 语言/框架/**ORM** 选型(Prisma/Drizzle/SQLAlchemy 等)、整体应用架构、服务划分 → dev-kickoff(技术方案)。本 skill 沿用技术方案已定的 ORM,但不替它做选型。
- ❌ 功能需求、用户故事、产品范围 → PRD(需求定义)。
- ❌ UI / 交互 / 信息架构 → UX 设计。
- ❌ 具体业务代码、查询语句实现、可执行的迁移脚本 → 开发落地阶段。
- ❌ 测试计划与质量门禁 → 测试与质量 skill。
- ❌ 数据库运维:备份、容灾、主从/分片部署、监控告警、性能调优排障 → 运维/SRE,不在本 skill。

如果用户在这一步开始聊"用 React 还是 Vue""这个接口怎么写",把它记一笔到「开放问题与假设」或提示归属的 skill,然后把话题拉回"数据到底怎么存"。
