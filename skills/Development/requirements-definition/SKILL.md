# 需求定义(PRD)

把一个还很模糊的想法,变成一份团队和 AI 都能据此往下走的需求文档。它要回答的只有一个问题:**我们要做什么、做到什么程度算完成**——不回答"用什么技术做"或"长什么样"。

## 为什么先做这件事

用户给的初始需求几乎总是不完整的("帮我做个网页""加个导出功能")。如果跳过澄清直接开干,后面会反复返工。这个 skill 的核心价值是:**在写一行代码之前,先把模糊的地方问清楚、把边界划明确、把"完成"的标准定下来**,并把结果沉淀成一份可以被后续所有阶段引用的文档。

## 何时触发哪条路径

先判断 `docs/PRD.md` 是否已存在:

- **不存在** → 走「新建需求」流程(结构化访谈 → 产出 PRD)
- **已存在**,且用户在新增/删除/调整某个需求 → 走「需求变更」流程(原地更新 + 追加变更记录)

## 新建需求流程

### 第 1 步:结构化访谈(关键步骤,别跳过)

不要拿到一句话需求就直接写文档。先主动把下面这些维度问清楚——这是 PRD 质量的根本来源。

**访谈原则:**
- **自适应,不要机械念题。** 用户已经说清楚的维度就别再问;一次问 2-4 个相关问题,别一口气抛八条让人窒息。
- **追着"为什么"问。** 用户说"要一个导出功能"时,真正要搞清的是"导出给谁看、解决他什么问题"——这决定了功能长什么样。
- **必须拿到用户的真实答复再动笔。** 用 AskUserQuestion 提问后要**等用户回答**,不要自己替用户假设答案、也不要跳过提问直接写文档——强制把需求问清楚,正是这个 skill 的价值所在。只有那些当下确实无法定夺的事项(例如依赖尚未做出的外部决策)才记进「开放问题与假设」;它是"现在没法定"的归档,不是"懒得问"的出口。

**需要覆盖的维度(用 AskUserQuestion 提问,给出带推荐的选项,降低用户负担):**

1. **问题与背景** — 要解决什么问题?为什么现在做?不做会怎样?
2. **目标与成功指标** — 怎么算成功?有没有可量化的指标(转化率、耗时、数量…)?
3. **目标用户与场景** — 谁用?主要角色是谁?最核心的使用场景/流程是什么?
4. **功能范围** — 这一期必须有哪些功能?哪些是 P0(没有就不算完成),哪些可以later?
5. **边界与非目标** — 明确**不做**什么?最容易被忽略,但能省掉大量后期扯皮。
6. **验收标准** — 每个核心功能,怎么样算"做完了、做对了"?
7. **约束** — 有没有功能层面的硬约束(合规要求、必须对接的已有系统、时间窗口)?注意:技术选型不在这一步问。

### 第 2 步:产出 PRD

访谈信息够了之后,读取 `assets/prd-template.md`,按它的结构产出文档,写入 `docs/PRD.md`(若 `docs/` 不存在则创建)。内容用**中文**。

要点:
- **功能需求按「功能模块 → 子功能」分层组织**,不要拉一个扁平的 F1…Fn 长列表:先按业务把功能归成几个模块(如"预订管理""会议室管理""通知"),再在每个模块下列子功能。每条子功能用**用户故事 + 优先级 + 验收标准三件套**表达:「作为<角色>,我想<做什么>,以便<价值>」,标 P0/P1/P2,每条都要有可检验的验收标准。一条没有验收标准的需求等于没定义清楚。
- **范围与非目标都要写实。** "不做什么"和"做什么"同样重要。
- 没问清楚的,如实写进「开放问题与假设」,不要假装确定。
- 文档头部填好状态、日期、负责人,方便后续维护。

产出后,简要告诉用户:PRD 写到哪了、有哪些开放问题需要他拍板,以及下一步通常是 UX 设计或开发 kickoff(由对应 skill 接手)。

## 需求变更流程

当 `docs/PRD.md` 已存在、用户要新增/删除/调整需求时:

1. **先读现有 PRD**,理解当前需求全貌,再动手——不要在没读全的情况下改。
2. **原地修改对应章节**(功能表、范围、验收标准等),保持文档始终是唯一、最新的事实源。
3. **在「变更记录」表追加一行**:日期、类型(新增/删除/变更)、内容、原因。变更记录是为了让任何人能看懂"这个需求为什么变成现在这样"。
4. 如果这次变更带出了新的不确定点,同样追加到「开放问题与假设」。

## 边界:这个 skill 不做什么

明确把这些留给后续阶段,避免越权:

- ❌ 技术栈选型、架构、依赖管理 → 开发 kickoff skill
- ❌ UI/视觉/交互设计 → UX 设计 skill
- ❌ 数据库表结构设计 → 数据库 skill
- ❌ 具体代码实现

如果用户在这一步就开始聊技术方案,可以记一笔到「开放问题与假设」,然后把话题拉回"我们到底要做什么"。
