# UX 交互设计

把 PRD 里说清楚的「要做什么」进一步翻译成「用户怎么用」——每一条功能对应什么操作路径、什么界面状态、什么反馈。这个 skill 回答的是：**用户在产品里经历什么，边界情况和错误发生时展示什么**——不回答"用什么技术做"或"视觉长什么样"。

## 为什么需要这一步

PRD 描述的是功能意图，但它不足以指导前端开发或评审——它不回答"空状态长什么样""加载失败该提示什么""用户填错表单后能做什么"。UX 文档填补这个空白，让后续的技术方案和开发都有依据，同时在写代码之前把边界情况暴露出来。

## 何时走哪条路径

先判断 `docs/UX.md` 是否已存在：

- **不存在** → 走「新建 UX 文档」流程（访谈 → 产出 UX.md）
- **已存在**，且用户在更新某个流程/模块/角色 → 走「UX 变更」流程（原地更新 + 追加变更记录）

## 新建 UX 文档流程

### 第 1 步：读 PRD（如果有）

先检查 `docs/PRD.md` 是否存在并读取——它是最重要的输入，里面有目标用户、核心场景、功能范围和验收标准。阅读时重点关注：
- 有哪些用户角色？各自的核心任务是什么？
- P0 功能有哪些？优先级顺序？
- 已有的约束（如：必须对接某个已有系统）
- 被标为「开放问题」的内容——这些往往需要在 UX 访谈里跟进

如果 PRD 不存在，告诉用户"还没有 PRD，建议先用 requirements-definition skill 产出一份，或者你先给我描述一下要做什么"，但不强制——用户可以直接口头介绍需求后继续。

### 第 2 步：结构化访谈（别跳过）

不要拿着 PRD 直接写 UX 文档。PRD 回答了"做什么"，但交互决策需要进一步澄清。用 `AskUserQuestion` 问——**等用户回答后再动笔**，不替用户假设。

**访谈原则：**
- PRD 已经写清楚的就别再问；一次 2-4 个相关问题，别一口气抛七八条。
- 追着"用户在这一步会做什么、期望看到什么"问，而不是停在功能层面。
- 只有真正当下无法定夺的（比如需要产品/设计师决策的）才记入「开放问题」；它是"现在没法定"的归档，不是"懒得问"的出口。

**需要覆盖的维度（根据 PRD 已有信息自适应，不要机械念题）：**

1. **用户角色与核心旅程** — 哪个角色是最主要的？他们最重要的一条从入口到完成的路径是什么？
2. **导航与信息架构** — 一级入口有哪些？内容怎么分组？不同角色看到的导航是否不同？
3. **关键流程决策** — 多步操作是线性向导式还是自由切换？中间能不能保存草稿/暂离？
4. **状态与反馈** — 操作成功/失败/加载中分别提示什么？空状态（第一次进来没有数据）显示什么？
5. **错误处理** — 表单填错了怎么提示（行内还是顶部）？网络断了怎么办？权限不足怎么引导？
6. **边界与非常规路径** — 并发操作（两人同时编辑同一条）、数据量很大时的分页/加载、删除/不可逆操作的确认机制。
7. **设备与输入方式** — 主要在 PC 浏览器还是移动端？是否需要考虑键盘导航？

### 第 3 步：产出 UX.md

访谈信息够了之后，读取 `assets/ux-template.md`，按它的结构产出文档，写入 `docs/UX.md`（若 `docs/` 不存在则创建）。内容用**中文**。

要点：
- **按「功能模块 → 具体界面/流程」分层组织**，不要拉一个扁平的大列表。
- 每个流程用「步骤 + 用户操作 + 系统响应」三件套描述，让开发能直接对照实现。
- **每个关键交互点都要有可检验的验收标准**（"用户点击提交，若必填项为空，提交按钮不可点击，且对应字段显示红色行内错误提示"——这是验收标准；"显示错误提示"——这不算）。
- 状态清单要穷举：正常态、加载态、空态、错误态、禁用态——至少把「在哪里用」明确标出，别只写"视具体情况"。
- 明确写「边界与非目标」，比如"本文档不涉及邮件通知的具体文案设计，那属于运营内容"。

产出后，简要告诉用户：UX 文档写到哪了、有哪些开放问题需要他拍板，以及下一步通常是技术方案（dev-kickoff skill）。

## UX 变更流程

当 `docs/UX.md` 已存在、用户要更新某个流程/界面/角色时：

1. **先读现有 UX.md**，理解当前交互全貌，再动手——不在没读全的情况下改。
2. **原地修改对应章节**（流程图、状态列表、交互说明等），保持文档始终是唯一最新的事实源。
3. **在「变更记录」表追加一行**：日期、类型（新增/删除/变更）、内容、原因。
4. 如果变更带出了新的不确定点，追加到「开放问题与假设」。

## 边界：这个 skill 不做什么

- ❌ 视觉设计（颜色方案、字体选择、间距规范、设计稿） → 留给设计师或视觉工具
- ❌ 前端代码实现 → 开发阶段
- ❌ 技术栈选型、组件库推荐 → dev-kickoff skill
- ❌ 数据库字段与表结构 → database skill
- ❌ 功能需求范围的增删改 → 回到 requirements-definition skill

如果用户在这一步开始聊"用 React 还是 Vue""选哪个 UI 库"，记一笔到「开放问题」，然后把话题拉回"用户操作这里时会发生什么"。
