# 开发启动技术方案(Dev Kickoff)

把已经明确的产品需求和交互方案,转换成开发可以据此开工的技术方案。这个 skill 回答的是:**用什么技术做、系统怎么拆、关键决策为什么这样定、哪里有风险**。它不回答"功能到底要不要做",也不展开到数据库表结构或具体业务代码。

## 为什么需要这一步

PRD 和 UX 让团队知道要做什么、用户怎么用,但开发启动前还需要一份共同的技术事实源:目标平台有哪些、客户端和服务端分别怎么选型、模块边界在哪里、哪些技术风险需要提前处理。如果跳过这一步直接写代码,后续很容易出现多端方案不一致、模块职责混乱、数据库/接口/部署决策互相牵扯的问题。

## 何时走哪条路径

先判断 `docs/TECH_DESIGN.md` 是否已存在:

- **不存在** -> 走「新建技术方案」流程(读取 PRD/UX 或访谈 -> 产出 TECH_DESIGN.md)
- **已存在**,且用户在调整平台、技术栈、架构、模块或风险决策 -> 走「技术方案变更」流程(原地更新 + 追加变更记录)

## 新建技术方案流程

### 第 1 步:读取已有输入(如果有)

优先检查并读取:

- `docs/PRD.md`:目标用户、核心功能、范围、非目标、验收标准、约束
- `docs/UX.md`:用户流程、页面/界面结构、状态与边界情况、多端/设备线索

这些文档是高价值输入,但不是硬前置。如果任一文档不存在,不要卡住;告诉用户缺少哪些输入,然后用访谈把本阶段需要的信息补齐。

阅读时重点提取:

- 产品类型和核心业务流程
- 目标平台:Android app、iOS app、Web、Windows 应用是否都需要;哪些是本期范围
- 认证、权限、通知、支付、文件、实时协作、离线能力等技术敏感功能
- 性能、安全、合规、部署、预算、团队经验等约束
- PRD/UX 中留下的开放问题,尤其是会影响架构和选型的问题

### 第 2 步:结构化访谈(别跳过)

不要只凭 PRD/UX 直接拍技术栈。技术方案依赖团队能力、平台范围、上线节奏、维护成本和外部约束,这些经常不在 PRD 里。用当前平台可用的提问机制(如 AskUserQuestion)向用户提问,并**等用户回答后再写正式 TECH_DESIGN.md**。不要替用户假设关键约束。

**访谈原则:**

- PRD/UX 已经写清楚的就别重复问;一次问 2-4 个相关问题。
- 追着"为什么这样选更适合这个团队和产品"问,而不是堆热门技术名词。
- 只有当下确实无法定夺、依赖外部决策的问题,才写进「开放问题与假设」。
- 如果用户已经明确要求某技术栈,仍要记录理由、风险和替代方案,不要无条件照抄成结论。

**必须覆盖的维度(自适应提问):**

1. **目标平台与优先级** — Android app、iOS app、Web、Windows 应用分别是否需要?本期先做哪些?
2. **客户端选型约束** — 是否接受跨端框架?是否需要原生能力、离线、推送、后台任务、系统集成?
3. **Web 与桌面策略** — Web 是管理后台、C 端应用还是营销站?Windows 是原生桌面、WebView 包壳还是 Electron/Tauri 类方案?
4. **后端与数据层选择** — 后端语言/框架、API 风格、ORM、缓存、队列、文件存储等大方向;只定技术策略,不展开数据库表结构。
5. **团队与交付约束** — 团队熟悉什么、预计维护多久、上线周期、部署环境、预算、合规要求。
6. **集成与风险** — 第三方服务、支付、地图、推送、身份提供商、企业系统对接、性能/安全/可靠性风险。

### 第 3 步:产出 TECH_DESIGN.md

访谈信息够了之后,读取 `assets/tech-design-template.md`,按它的结构产出文档,写入 `docs/TECH_DESIGN.md`(若 `docs/` 不存在则创建)。内容用**中文**。

要点:

- **多端技术栈必须分开写。** 至少按 Android app、iOS app、Web、Windows 应用分别说明:是否本期建设、推荐技术栈、理由、关键风险、替代方案。没有目标平台也要标明"本期不建设/待确认",不要省略。
- **架构按层和模块组织。** 先讲客户端、后端、数据访问、集成、部署/运维等层次,再列模块职责;不要把所有组件拉成一个扁平列表。
- **每个关键技术决策都要有理由和取舍。** 写清选择什么、不选什么、为什么适合当前约束。
- **每个核心模块都要有可检验的评审标准。** 例如"认证模块必须支持登录态过期后的统一刷新/退出路径,并能在 Web 与移动端复用同一套 token 策略"。
- **守住边界。** 可以选择数据库类型、ORM、迁移工具、缓存/队列策略;不要写具体表、字段、索引和外键,这些交给 database skill。
- **把开放问题显式列出。** 不能确定的技术前提不要假装已经拍板。

产出后,简要告诉用户:TECH_DESIGN 写到哪里、最重要的技术决策是什么、有哪些开放问题,以及下一步通常是 database skill 做 `docs/SCHEMA.md`。

## 技术方案变更流程

当 `docs/TECH_DESIGN.md` 已存在、用户要调整技术栈/架构/模块/平台范围时:

1. **先读现有 TECH_DESIGN.md**,理解当前方案全貌,再动手。
2. 如有 PRD/UX 变更,同步读取相关文档,确认变更来源。
3. **原地修改对应章节**,保持 `docs/TECH_DESIGN.md` 是唯一最新的技术事实源。
4. **在「变更记录」表追加一行**:日期、类型(新增/删除/变更)、内容、原因。
5. 如果变更影响 database 或 testing-quality 阶段,在「下游影响」里明确标出,但不要替下游 skill 完成其文档。

## 边界:这个 skill 不做什么

- ❌ 功能范围、用户故事、产品验收标准 -> requirements-definition skill
- ❌ 用户流程、页面状态、交互反馈、视觉设计 -> ux-design skill 或设计工具
- ❌ 数据库表结构、字段、索引、外键、迁移脚本细节 -> database skill
- ❌ 测试用例、覆盖率门禁、验收测试矩阵 -> testing-quality skill
- ❌ 具体业务代码、组件实现、接口实现 -> 开发实现阶段

如果用户要求直接写表结构或代码,先把必要的技术决策记录到 TECH_DESIGN,再提示这些内容应交给后续阶段处理。
